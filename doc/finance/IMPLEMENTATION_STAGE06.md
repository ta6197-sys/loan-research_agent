# 6단계 — 답변·정정 후 새 판 갱신

2026-10-21 사용자 선택: **일반 신규 기업 자동 수집보다 기존 사례의 답변·정정 후 새 판 갱신을 먼저 구현**한다. 기존 버전 보존·자동 게시·현재 입력 고정·메모 명시 반영·새 실행 한도와 누적 사용량 정책을 유지했다.

현재 완료한 범위는 **보관한 상신브레이크 사례의 텍스트 답변/정정 접수 → 관련 공시 재검색·원문/수치 재검증 → 로컬 모델 → 새 판 게시**다. 일반 첨부·외부 신규 재수집·전체 장애 복구·화면을 포함한 6단계 전체 완료로 표시하지 않는다. 실제 회사 내부자료를 받은 시험도 아니다.

## 사용자가 보게 되는 동작

1. 보고서 질문에 답하거나 정정을 요청하면 입력 ID·수신 시각·적용 기준·대기 실행 ID를 받는다. 처리 중에도 이전 게시본은 유지된다.
2. 아직 시작하지 않은 같은 기준의 입력은 이력을 각각 보존해 함께 처리한다. 이미 실행 중이면 그 실행에 끼워 넣지 않고 다음 실행으로 넘긴다.
3. 관련 항목을 다시 확인하고 새 판을 게시한다. 이전 판과 정정 요청·답변의 원문을 계속 조회할 수 있다.
4. 사용자 설명은 `user_provided_unverified`로 보존한다. 답변이 연결된 질문은 `answered_unverified`(답변 수신·검증 전)이며, 독립 근거가 부족하면 미확인과 추가 요청을 유지한다. 사용자가 금액을 정정했다고 공시 수치를 바꾸지 않는다.
5. 일반 메모는 저장만 한다. ‘조사에 반영’한 메모만 후속 실행을 만든다. 중단하면 같은 조사의 실행 중·대기 작업을 멈추고, 이후 답변 수신이나 서버 재시작이 중단을 취소하지 않는다.

## 저장·실행 경계

`agent/finance/research_followup.py`는 기존 불변 이벤트·원문·실행 테이블을 재사용한다. 입력 수신 이벤트를 먼저 기록하고 원문 쓰기 일지/복구 및 입력별 잠금으로 같은 원문을 중복 등록하지 않는다. 같은 요청 키의 다른 내용은 거부한다. 같은 보고서·내용·종류·질문을 새 키로 재전송해도 기존 입력을 재사용하고 키별 중복 이력을 남긴다. 재전송은 새 한도나 새 판을 만들지 않는다.

실행 시작 트랜잭션에서 입력 ID·원문 ID·실제 직전 게시본·기준·재사용 수치 실행·영향 항목을 고정한다. 시작 전 입력 원문 저장이 미완료면 대기한다. 처리 중 추가 입력은 새 후속 실행에만 들어간다. 같은 회사라도 기준 버전이 다르면 근거를 조용히 혼합하지 않는다.

새 답변/정정에는 새 실행 한도 스냅샷을 적용하고 전체 누적 사용량을 표시한다. 기존 실행의 사용량은 보존한다. 수치와 계산은 같은 기준의 기존 근거 ID·검증 배치를 재검증해 재사용한다. 전체 자료를 복제해 확인 플래그만 옮기지 않는다. 표·차트 값은 사용자 설명이나 모델 출력에서 만들지 않는다.

일곱 항목 중 연결된 쟁점을 중심으로 보관 공시를 재검색한다. 차입 질문은 차입, 자금 용도/상환은 현금흐름·목적, 범위/버전은 재무·공시 항목이다. 특정 쟁점이 없는 정정은 전 항목을 재검색한다. 관련 없는 항목의 기존 확인 범위는 재사용하고 수치 근거의 원문 위치/해시는 다시 검사한다. 외부 최신 정정공시나 은행 내부 자료를 새로 확보한 것으로 소개하지 않는다.

진행 중 모델 결과가 늦게 돌아와도 중단 상태를 확인한 뒤 새 호출·게시를 거부한다. 프로세스 내 후속 대기 작업은 API 연결과 독립적으로 실행한다. 서버 종료 시 작업을 취소하고 실행은 `interrupted`로 남긴다. 이후 [7단계](IMPLEMENTATION_STAGE07.md)에서 서버 내부 저장형 실행 관리자의 자동 복구·명시 재개를 연결했다. 별도 워커를 추가한 것은 아니다.

## API

연구 모드와 기존 로컬 Host/Origin 통제를 적용한다.

```http
POST /researches/{research_id}/inputs
Content-Type: application/json

{
  "parent_report_id": "게시된 보고서 ID",
  "request_key": "메시지별 고유 키",
  "kind": "answer",
  "text": "답변 또는 정정 요청 내용",
  "question_ids": ["U_repayment"],
  "reflect_in_research": false
}
```

응답은 202이며 `input_id`, `source_id`, `run_id`, `basis_id`, `received_at`, `status`를 반환한다. `question_ids`는 현재 사례의 `U_borrowing`, `U_working_capital`, `U_repayment`, `U_scope` 쟁점 ID다. `kind`는 `answer`/`correction`/`memo`, `reflect_in_research`는 메모의 명시 반영 여부다. 기업·목적·기준일·파일 경로·도구·임의 URL 실행 인자를 추가로 받지 않는다.

`POST /researches/{id}/stop`은 같은 조사의 대기 작업까지 중단한다. 기존 `GET /reports/{id}`, `GET /researches/{id}/reports`, `/events`, `/runs/{id}`, `/sources/{id}/view`로 버전·진행·근거를 조회한다. 금융 Vue 화면·첨부 전송은 별도 구현 대상이다.

## 시험 결과와 한계

합성 수용 시험 10개가 답변 후 새 판·기존 수치/미확인 보존, 중복 키/내용·키 충돌, 메모 명시 반영, 실행 중 입력 고정/다음 판, 중단 후 늦은 결과/대기/새 입력 차단, 다른 조사·변경 기준·없는 질문 거부, 악성 정정의 수치 덮어쓰기 차단, 원문 저장 실패 후 같은 입력 복구, 시작 실패의 무한 반복 차단, API 자동 처리를 확인했다. 최종 전체 시험은 250개 통과(실패/오류/건너뜀 0)다.

실제 보관 자료와 로컬 `qwen3.5:2b`를 연결한 새 분석 복사본:
`data/research/validation_stage06/20261021T084149Z-6f04ab4a/`.

- **합성 답변**으로 5판(현금흐름·목적), **합성 정정 요청**으로 6판(차입)을 게시했다. 실제 회사 답변이나 내부자료가 아니다.
- 두 실행 모두 첫 응답의 미확인 ID 누락을 검증기가 거부했다. 허용된 검증 피드백 후 통과했으며 모델 호출 각각 2회/20회, 실행 시간 각각 47초/41초였다. 최초 실행의 9회는 그대로 보존했고 이 분석의 누적 모델 사용량은 13회다.
- 기존 130칸(114확인/16보류)·차트와 미확인 4개를 유지했다. 답변 수신으로 상환재원·차입 만기를 확인 완료로 바꾸지 않았다.
- 원본 분석 DB의 13,979개 행이 복사본에 그대로 존재하고 원문 89개가 양쪽 해시와 일치했다. HTTP 서버 두 프로세스(86794/86796)에서 1~6판의 모든 내용이 동일했다. 재조회 중 보호 파일 335개 변경/삭제 0, 모델/외부 요청 0이다.
- 최초 실모델 시험의 마지막 보존 검사는 목록/상세 필드 차이로 실패했다. 비교 코드를 고쳤고 **기존 5·6판을 재생성하지 않고** 사용량·자료·모델 계약·원본 행·원문·HTTP 조회를 재검증했다. 최초 실행 전 전체 파일 지문은 파일로 남기지 못했으므로, 그 시점부터의 전체 파일 보존 수치로 확대하지 않는다. 이후 재조회 구간의 파일 지문과 원본/복사본 행·원문 비교만 확인했다.

최종 재검증: `publication_readback.json`. 최초 실행의 `result.json`은 마지막 검사 실패로 생성되지 않았으며 숨기거나 성공 파일로 바꾸지 않았다. 이후 신규 실행용 `sh/verify_stage06_followup.py`는 실행 전 지문을 먼저 저장하도록 고쳤다. 기존 결과를 검사할 때는 다음 명령을 사용하며 모델을 다시 부르지 않는다.

```bash
.venv/bin/python sh/verify_stage06_readback.py \
  data/research/validation_stage06/20261021T084149Z-6f04ab4a \
  data/research/validation_stage05/20261021T080900Z-234e0dad
```

새 실제 DART 요청·외부 모델·외부 추적은 0이다. 종전 수집 예산 12/20, 추가 확보 15/20은 변경하지 않았다. 금융 자료 전체 확인은 여전히 미완료다. 일반 신규 기업 수집·첨부/OCR·은행별 일정의 독립 검증·에이전트 검토 질문의 추가 조사·금융 화면/출력·실무 비교 평가는 남아 있다. 이후 보관 사례의 실행 복구는 7단계에서 연결했다.
