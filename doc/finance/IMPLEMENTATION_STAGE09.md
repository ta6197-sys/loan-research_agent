고정 절차는 같은 일곱 항목·검색어·수치 검사·모델·게시 검사를 순차 실행한다. 에이전트는 기존 LangGraph를 실행한다. 양쪽이 같은 최초 조사 코드를 공유하므로 독립 구현의 조사 능력 비교가 아니다. 현재 최초 조사의 자율 계획/추가 검색 효과를 이 비교로 입증할 수 없다. 실행 순서는 고정1→에이전트1→에이전트2→고정2→고정3→에이전트3이다. 순서는 평가 전에 고정했으며 무작위 배정이라고 표현하지 않는다.

앱 DB/검증 결과 캐시는 회차마다 새로 만들고 원문 접근 범위는 같다. Ollama 프롬프트 캐시·OS 캐시는 초기화하지 않았고 일부 회차에 합성 회귀 시험이 동시에 실행됐다. 실행 시간은 관측값이며 처리 방식만의 속도 차이나 담당자 업무 시간 절감률로 해석하지 않는다. 실제 담당자의 재확인 시간·질문 유용성·외부 대기 시간은 측정하지 않았다.

## 기준표

평가 시작 전에 기존 수작업 `financial_evidence.json`의13계정×5시점×2범위=130칸을 준비했다. 별도 보관 API 파일의 법인·계정 ID·재무제표·접수번호·금액 필드를 다시 읽어 수작업 원 단위 값과 대조한다. 정답 값을 새 실행 결과에서 가져오지 않는다. 다만 차입 구성 사용 가능/보류 정책은 고정4단계 검증 기록을 공유한다. 구성 안전성 판단까지 독립된 정답표인 것은 아니다.

확인 가능114칸과 구성 보류16칸을 분리한다. 16칸을 값이 틀린 오류로도, 모두 확인된 칸으로도 세지 않는다. 나머지 확인 가능 항목을 빠뜨리면 공개 수치 누락으로 기록하고, 보류에 숫자를 게시하면 오류로 기록한다. 같은 숫자의 다른 범위/기간 연결·단위·중복·근거 없는 값도 검사한다. `build_view`가 게시/검증/원문 위치·해시를 다시 읽어 근거 추적을 확인한다. 별도 평가기 시험은 잘못된 값·범위·날짜·단위·누락·보류 승격이 통과하지 않는지 검사한다.

수작업 초안에서 별도6개 내용 점검표를 준비했다: 현금흐름의 채권/재고/매입채무 조정, 비현금 환산손익, 후속 보증, 감사의견/핵심감사사항, 소송, 사업 구조. 검색 발췌의 단어 존재는 후보일 뿐 의미 검증 통과가 아니다. 이6개는 전체 최소 확인표의 완전한 정답집이 아니며 기존 수작업 초안도 은행 전문가 검증본이 아니다. 원인 설명 전체·일곱 항목 충족·질문 유용성을 자동 검사로 인증하지 않는다.
