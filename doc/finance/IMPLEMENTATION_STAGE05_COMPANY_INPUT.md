# 5단계 보완 — 회사 입력부터 첫 초안까지

2026-10-21 사용자9번 선택: **상신브레이크 보관 자료로 먼저 연결**한다. 신규 외부 조회·다른 기업·새 공개 기준일은 이번 승인의 범위에 넣지 않았다. 기존 로컬 Ollama/qwen3.5:2b·외부 모델/추적 차단·원본 보존·미확인 유지 결정을 그대로 적용했다.

현재는 **빈 조사 DB → 회사 입력 한 번 → 새 조사/실행 대기 → 보관 공식 원문 준비 → 새 근거 추출·검증 → 일곱 항목·표/차트 → 로컬 초안 → 게시본**이 연결됐다. 이전에는 자료가 이미 들어 있는 실행ID를 직접 지정해야 했다. 일반 신규 기업 자동 수집이나 금융 화면/PDF 출력의 완성은 아니다.

## 회사 입력과 자료 준비

`GET /case-companies?query=상신`은 등록한 보관 사례만 검색하고 외부 DART 기업 목록을 조회하지 않는다. 현재 상신브레이크 회사명·법인코드00129642·종목코드041650으로 선택할 수 있다. 표시되는 자료는 공개 기준일2026-10-20의 보관 자료이며 최신 정정공시를 새로 확인한 것이 아니다.

`POST /researches/start`가 회사·목적·요청 키를 받아 새 조사와 고정 대기 실행을 같은 저장 트랜잭션에서 만든다. 별도 자료 제출·조사 시작 단계를 추가하지 않았다. 202응답 후 기존 실행 관리자가 처리하며 접속 종료와 조사 수명을 분리한다. 기존 저장 전용 `POST /researches` 계약도 유지한다.

```http
POST /researches/start
Content-Type: application/json

{
  "company": "상신브레이크",
  "purpose": "공개 자료를 활용한 운전자금 사전조사",
  "public_cutoff": "2026-10-20",
  "request_key": "회사 입력 메시지의 고유 키"
}
```

응답의 `research_id`, `run_id`, `status`, `reports_url`, `execution_url`로 진행·첫 게시본을 조회한다. 같은 요청/내용 재전송은 같은 조사·실행으로 돌아가며 새 모델 한도를 만들지 않는다. 같은 키의 목적/기준/예산 변경은 거부한다. 지원하지 않는 회사·다른 기준일·임의 파일 경로를 조용히 혼합하지 않는다. 보관 실행의 외부 요청 한도는0이며 모델20회·시간1800초 이내, 초안 시도 최대3회다.

## 원본·이용 제한·검증 경계

`cached_case.py`의 사례 목록은 승인한4단계 분석 DB를 SQLite `mode=ro`로 읽어 만든다. 등록 파일에는 회사/기준/기간·원본 DB해시·공식 출처 목록과 콘텐츠 해시를 고정한다. 원문 해시/경로/심볼릭 링크·허용 출처·참조 관계를 검사한다. 호출자가 경로나 자료 집합을 지정하는 API는 없다.

실제 등록은 `data/research/case_library/sangsin-20261020.json`이며 원본은 `data/research/validation_stage04_integrated/20261021T091006Z-ed3d0de8/`다. 등록 파일은 기존 것이 다르면 덮어쓰지 않는다. 자료가 없거나 바뀌면 명시적으로 중지하며 외부 조회로 자동 대체하지 않는다. 배포ZIP에서는 원문과 등록 파일 모두 `data/research` 제외 규칙을 적용한다. 원본을 배포에 포함한 것으로 소개하지 않는다.

새 조사에는89개의 공식 원문만 새 출처로 저장한다. 출처 종류·권리·이용 제한·외부 모델/추적 금지와 원래 바이트를 보존한다. `archive_source_id`·`referring_source_id`·정정 관계는 새 출처 ID로 변환하며 원래 ID/해시도 유래 정보로 남긴다. 사용자 답변·이전 보고서·확인 플래그·계산·검증 행은 복사하지 않는다. 새 조사에서 추출·수치/구성·XBRL 검증을 다시 수행한다.

중간에 멈춘 자료 준비는 이미 등록한 출처를 해시/메타데이터로 대조해 재사용한다. 원문 저장 일지 복구와 실행별 잠금을 적용하고, 등록된 목록 외의 출처나 위조 유래 정보가 섞이면 거부한다.7단계의 입력 고정·중단/재개·모델 시도/시간 한도·게시 소유자 검사를 함께 사용한다.

회사 입력만으로 법인 식별·금융 확인 전체를 완료 처리하지 않는다. 공시 원문/API의 회사 코드·범위·기간·단위·위치를 다시 확인하고 부족한 상세·범위/버전 대응은 보류한다.

## 검증 결과

추가 합성 시험9개가 회사 입력의 원자적 대기 생성, 중복/다른 내용 거부, 다른 회사·기준·과도한 예산 거부, 출처 참조 변환·기존 확인 플래그 미복사, 중간 준비 실패 후 재사용, 원본/등록 파일 훼손 거부, 목록 밖 출처 거부, 고정 목록 불일치 거부, 외부 요청 없는 검색·단일 입력API를 확인했다.

실제 회사 입력 시험:
`data/research/validation_stage05_input/20261021T092833Z-3a4fe222/result.json`.

- 빈 DB에서 회사 입력 한 번으로 새 조사/실행을 만들고 첫 보고서1판을 게시했다. 기존 조사DB/보고서의 복사본을 출발점으로 사용하지 않았다.
- 원문89개를 새 출처로 준비하고 새 근거·검증을 생성했다. 일곱 항목·130칸 중114확인/16보류와 기존 차트/미확인4항목의 상태를 유지했다.
- 실제 로컬 qwen3.5:2b1회 호출로 모델 계약을 통과했다. 실행 사용량49초·외부 요청0·외부 추적0이다. 이49초는 한 번의 개발 시험이며 일반 기업/장비의 성능 보장이 아니다.
- 같은 입력 재전송이 같은 조사/실행을 반환했고 게시본/모델 사용량도 늘리지 않았다. 서로 다른HTTP 서버89088/89090에서 같은 보고서와 사용량을 재조회했다.
- 원본 분석/등록 파일161개는 실행 전 지문과 비교해 변경/삭제0이다. 기존 수집 예산12/20·추가15/20을 초기화하거나 사용하지 않았다.

최초 검증 스크립트가 보고서 목록을 읽은 직후 게시가 완료되는 경합을 실패로 판단했다. 제품에서는 이미 정상 게시됐으며, 스크립트를 고쳐 **같은 DB·조사·보고서**를 재조회했다. 모델을 다시 호출하거나 새 실행/한도를 만들지 않았다. `existing_execution_rechecked=true`와 사용량1회를 함께 기록했다. 실패한 검증을 숨겨 새 시험 횟수로 바꾸지 않는다.

전체 회귀/4단계 원문 재대조·고장8종·MCP/HTTP 재시작·원본 보존 검사는 `data/research/validation_stage04_completion/20261021T093038Z-33bb65c0/verification.json`에서271개 통과(실패/오류/건너뜀0)다. 현재 소스 지문을 최종 확인한다. 개발 구현 완료와 실제 금융 필수/추가/전체 미완료는 유지한다.

## 실행·재검증

자료가 이미 등록된 현재 개발 환경에서는 `bash sh/run_research.sh` 후 위API를 한 번 호출한다. 실행 관리자에 저장된 승인 작업이 있으면 시작 시 이어간다. 보관 자료가 없는 배포본은503으로 알리며 원문을 임의 다운로드하지 않는다.

기존 등록은 그대로 보존하며, 승인된 원문이 있는 환경에서만 다음 명령으로 등록한다.

```bash
.venv/bin/python sh/register_cached_case.py \
  data/research/validation_stage04_integrated/20261021T091006Z-ed3d0de8
```

이미 생성된 시험의 모델을 다시 실행하지 않고 재조회하려면:

```bash
.venv/bin/python sh/verify_stage05_company_input.py --existing \
  data/research/validation_stage05_input/20261021T092833Z-3a4fe222
```

인자 없이 검증 명령을 실행하면 새 빈 분석DB에서 새 입력 시험과 로컬 모델 호출을 수행하므로 단순 재조회와 구분한다.
